# 관리자 신고 조회·삭제·메일 안내

최신 Develop의 글 작성·참가·신고 기능과 함께 동작하는 백엔드다. 프론트 연결과 배포용 세션 저장소 설정은 별도 작업이다.

## 관리자 인증

기존 로그인 세션 쿠키를 사용한다. 매 요청마다 DB에서 사용자와 현재 권한을 다시 확인한다.

- 로그인하지 않았거나 세션 사용자가 삭제된 경우: `401 UNAUTHORIZED`.
- 일반 사용자: `403 FORBIDDEN`.
- 관리자 여부는 요청 본문이나 쿼리에서 받지 않는다. 회원가입으로 ADMIN을 지정할 수 없다.
- 관리자 응답에는 `Cache-Control: no-store`를 설정한다.

기존 가입 계정에 관리자 권한을 부여하려면 저장소를 운영하는 개발자가 backend 폴더에서 실행한다. 이 작업으로 실제 사용자 권한을 자동 변경하지는 않는다.

```powershell
npm.cmd run set-admin -- registered-email@example.com
```

## 신고 글 목록

`GET /api/admin/accuse?page=0&size=20`

`page`는 0 이상의 정수, `size`는 1~100이며 기본값은 각각 0, 20이다. 삭제되지 않은 신고 글을 글 단위로 묶고 최신 신고 시각 내림차순, 동일 시각에는 글 번호 내림차순으로 정렬한다.

```json
{
  "items": [
    {
      "writingId": 1,
      "title": "공동구매 제목",
      "content": "글 본문",
      "photoUrl": "/images/photo.png",
      "authorId": 10,
      "authorName": "작성자",
      "reportCount": 1,
      "latestReportAt": 1700000000000,
      "reports": [
        {
          "id": 3,
          "reporterId": 20,
          "reporterName": "신고자",
          "reason": "신고 사유",
          "createdAt": 1700000000000
        }
      ]
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "hasNext": false
}
```

`totalElements`는 신고 건수가 아닌 신고된 글 개수다. 글별 `reports`는 최신 신고순이다. 결과가 없으면 `items: []`를 반환한다. 비밀번호·이메일·학번은 반환하지 않는다. 프론트에서는 제목·본문·사유를 텍스트로 표시해야 한다.

## 관리자 글 삭제

`DELETE /api/admin/{writingId}`

```json
{ "reason": "학교 규정에 어긋나는 물품입니다." }
```

삭제 사유를 제공하면 앞뒤 공백을 제거한 길이가 1~1,000자여야 한다. 최신 Develop과의 호환을 위해 이 경로에서 사유를 생략하면 '관리자 검토 후 삭제되었습니다.'를 사용한다. 직접 입력한 사유를 반드시 요구하는 기존 경로 `DELETE /api/admin/writing/{writingId}`도 유지한다. 신고 여부와 관계없이 관리자만 삭제할 수 있다. 성공 응답은 `204`이며 본문이 없다.

- 글에 삭제 시각·관리자 ID·사유를 기록하고 작성자 안내 메일 발송 대기 기록을 같은 트랜잭션으로 저장한다.
- 수신 주소는 DB의 글 작성자 이메일을 사용한다. 요청의 수신 주소나 관리자 ID는 반영하지 않는다.
- 삭제된 글은 기존 목록·메인 목록·상세·마이페이지·참가·탈퇴·모집 마감·신고와 관리자 신고 목록에서 제외된다.
- 참가 기록과 신고 기록은 보존한다. 같은 글을 다시 삭제하면 `404 POST_NOT_FOUND`이며 메일을 추가로 생성하지 않는다.
- 일반 작성자의 기존 글 삭제 API는 그대로이며 관리자 삭제 안내 메일을 생성하지 않는다.

오류 형식은 `{ "code": "...", "message": "..." }`이다.

| HTTP | code | 조건 |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | 페이지·크기·글 번호·삭제 사유·JSON 형식 오류. `fieldErrors` 포함 |
| 401 | UNAUTHORIZED | 로그인 없음 또는 세션 사용자 없음 |
| 403 | FORBIDDEN | 관리자 권한 없음 |
| 404 | POST_NOT_FOUND | 대상 글 없음 또는 이미 삭제됨 |
| 413 | PAYLOAD_TOO_LARGE | 요청 본문 크기 제한 초과 |
| 500 | INTERNAL_SERVER_ERROR | 저장 처리 실패. 이 경우 트랜잭션을 되돌려 글 삭제도 취소 |

## 삭제 안내 메일

기존 `.env`의 `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` 설정을 함께 사용한다. 본문은 글 번호·제목·관리자가 입력한 삭제 사유·삭제 시각(UTC)을 포함하는 일반 텍스트다.

`npm.cmd start` 또는 `npm.cmd run dev`로 서버를 실행하면 시작 시와 이후 5초마다 대기 알림을 확인한다. 한 번에 최대 10건을 처리한다. 삭제 API는 메일 전송을 기다리지 않고 DB 저장 후 응답한다.

- 메일 실패 시 글 삭제와 삭제 사유는 유지된다.
- 최대 5회 시도하며 실패 후 1·2·4·8분 간격으로 재시도한다. 전송 중 예약은 2분 동안 유지한다.
- 성공 시 `sent_at`을 기록하여 다음 처리에서 제외한다. 실패 내역은 알림 번호와 시도 횟수만 서버 로그에 남긴다.
- 5회 실패한 알림은 DB에 남으며 자동 발송을 중단한다. 메일 설정 복구 후 운영자가 해당 알림의 `attempts`, `next_attempt_at`을 확인하고 재처리 여부를 결정한다.
- 메일 서버가 수락한 직후 앱이 중단되는 경우에는 재시도 과정에서 중복 수신 가능성이 있다. 외부 메일 전달과 DB 기록을 하나의 트랜잭션으로 묶을 수는 없다.

테스트는 격리된 DB와 가짜 메일 전송기를 사용한다. 실제 SMTP 수신과 프론트 연결은 별도 확인해야 한다.

## 기존 DB

서버 초기화 시 `writings.deletion_reason`과 `deletion_notifications`를 추가한다. 기존 사용자·글·참가·신고 기록과 이전 발송 대기 기록은 보존한다. 이전 대기 기록에 사유 열이 없으면 기본 안내 문구를 채운다.

현재 구현에서는 신고 등록 경로 `POST /api/writing/accuse/{writingId}`와 친구가 만든 글 관련 코드를 변경하지 않는다.
